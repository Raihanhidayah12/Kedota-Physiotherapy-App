    Peta layar ke API:
    - Daftar/masuk dengan nomor HP: GET /rest/v1/profiles (lookup profil dan
      PIN hash pada kode saat ini), lalu POST /auth/v1/token?grant_type=password.
      Pemulihan session memakai POST /auth/v1/token?grant_type=refresh_token.
    - Daftar akun: POST /auth/v1/signup lalu POST /rest/v1/profiles (upsert).
    - Masuk Google/Apple: POST /auth/v1/token?grant_type=id_token pada alur
      native, atau GET /auth/v1/authorize pada alur OAuth redirect; profil
      dibaca/dibuat melalui /rest/v1/profiles.
    - OTP email: POST /auth/v1/otp dan POST /auth/v1/verify; status email
      diperbarui melalui PATCH /rest/v1/profiles.
    - OTP nomor HP untuk beberapa layar, termasuk lupa PIN dan ubah nomor,
      masih diverifikasi secara lokal dengan kode demo. Itu bukan request OTP
      yang diverifikasi Supabase dan tidak aman untuk pemakaian produksi.
    - Splash, Profil, Pengaturan, Edit Profil, dan data foto: GET/PATCH
      /rest/v1/profiles, upload ke /storage/v1/object/... dan baca URL public.
    - Home, Janji Temu, Riwayat, Progress, Detail, notifikasi, dan pilihan
      slot: GET /rest/v1/appointments; pembuatan reservasi memakai POST yang
      sama. Data klinis pada detail dibaca dari kolom appointment.
    - Expiry, reschedule terkontrol, dan pelunasan: POST ke RPC
      expire_overdue_appointments, reschedule_appointment, dan
      settle_appointment_payment.
    - Sebagian penyimpanan status notifikasi, preferensi, OTP telepon, serta
      autentikasi biometrik dilakukan lokal di device; fitur-fitur tersebut
      tidak memiliki endpoint Supabase tersendiri.
    - Perubahan PIN dengan session aktif memakai PATCH profiles dan PUT
      /auth/v1/user. Lupa PIN memakai POST /functions/v1/update-pin; OTP yang
      mendahului request ini belum diverifikasi oleh server.
    - Error HTTP 5xx dari client dikirim ke POST
      /functions/v1/client-error-log. Pembayaran masih demo, tanpa gateway
      atau webhook production.

    Catatan implementasi:
    - PIN di-hash menggunakan SHA-256 sebelum disimpan ke kolom pin_hash.
    - Auth email untuk signup phone menggunakan email asli user (jika valid),
      fallback ke format {digits}@kedota.local.
    - Reset PIN tanpa session diarahkan ke Edge Function update-pin; keamanan
      alur ini belum production-ready sampai OTP dibuktikan oleh server.
      Ganti PIN dengan session aktif memakai PATCH profiles dan Supabase Auth
      user update.
    - Edge Function client-error-log menerima metadata response HTTP 5xx dari client.
    - Password Supabase Auth disinkronkan pada alur ganti/reset PIN.
    - Nomor telepon selalu disimpan dalam format +62xxx (dinormalisasi via PhoneValidator.normalizePhoneNumber() di createPhoneProfile, signInWithPhone, completeSocialProfile, dan createPhoneProfileAndPin).
    - Aturan perubahan kontak dan limit OTP di UI bukan validasi server yang
      lengkap. OTP nomor HP pada alur perubahan kontak adalah demo lokal;
      email menggunakan Supabase Auth OTP.

    Catatan kesesuaian database dan keamanan:
    - Migration repository mendefinisikan profiles, appointments, error_logs,
      tiga RPC, bucket profile-photos, trigger, indeks, dan RLS.
    - RLS owner-only pada profiles di migration belum kompatibel dengan
      pencarian profil pra-login yang dilakukan aplikasi. Login nomor HP
      saat ini juga membaca pin_hash dan membandingkan hash di client; lookup
      semua baris profil sebagai fallback tidak aman. Perlu mekanisme server
      terbatas sebelum menerapkan RLS tersebut ke project live. Jangan membuka
      SELECT seluruh profil untuk mengatasi masalah ini.
    - PATCH appointment langsung dari salah satu alur edit reservasi hanya
      divalidasi oleh client untuk jendela waktu. Gunakan RPC
      reschedule_appointment untuk validasi server-side.
    - Migration hanya mendefinisikan struktur; tidak membuat data pasien,
      appointment, atau data klinis. Status schema dan data project live belum
      dapat dipastikan dari repository.

    DATABASE SCHEMA:
    Definisi kolom lengkap untuk ketiga tabel saat ini tersedia pada
    components/schemas Profile, Appointment, dan ErrorLog. Ekstensi
    x-database pada masing-masing schema merangkum tipe DB, nullability melalui
    properti nullable, default, primary/foreign key, constraint, dan index
    berdasarkan migration repository. Ini adalah baseline yang harus
    dicocokkan saat database pengganti dirancang; screenshot hanya memastikan
    nama tabel, bukan detail DDL live.
    Tabel `profiles` memiliki struktur:
    - id (UUID, PK)
    - phone (String)
    - full_name (String)
    - email (String)
    - auth_email (String)
    - pin_hash (String, SHA-256)
    - birth_date (Date, YYYY-MM-DD)
    - gender (Enum: Laki-laki, Perempuan, Lainnya)
    - signup_method (Enum: phone, google, apple)
    - status (Enum: active, deactivated, recycled)
    - is_profile_complete (Boolean)
    - nik (String, 16 digit)
    - address (String)
    - medical_code (String, format KDT- + 12 karakter heksadesimal)
    - email_verified (Boolean, default false — true setelah pengguna memverifikasi email)
    - profile_photo_url (String, opsional)
    - last_login_at (Timestamp)
    - created_at, updated_at (Timestamp)
    - phone_changed_at (Timestamptz, nullable) — timestamp perubahan nomor HP terakhir; digunakan untuk rate-limit 1x/hari
    - email_changed_at (Timestamptz, nullable) — timestamp perubahan email terakhir; digunakan untuk rate-limit 1x/hari

    Tabel `appointments` menyimpan satu jadwal terapi per record dan digunakan
    untuk Home, Riwayat, Progress, notifikasi, reschedule, dan pembayaran.
    Pasien yang dibooking, pilihan layanan/terapis, rincian harga, serta data
    klinis tersimpan dalam kolom row appointment (lihat skema lengkap), bukan
    relasi ke tabel terpisah dalam baseline sekarang.
    Tabel `error_logs` menyimpan metadata error 5xx melalui Edge Function;
    client tidak diberi akses REST langsung ke tabel tersebut. Model data
    terpisah untuk audit log yang dihapus/retensi tidak terlihat pada kontrak
    saat ini.

    Konfigurasi Maps & Geocoding:
    Aplikasi menggunakan sistem 3 tier cascading fallback untuk peta dan geocoding
    di alur reservasi Home Care:
    - Tier 1 (Utama): Google Maps API — tile dan geocoding premium
    - Tier 2 (Sekunder): Geoapify — tile osm-bright dan geocoding (3000 req/hari gratis)
    - Tier 3 (Tersier): OpenStreetMap/Nominatim — tile standar dan geocoding gratis unlimited
    Konfigurasi: GOOGLE_MAPS_API_KEY dan GEOAPIFY_API_KEY di file .env client.
    Pergantian layanan terjadi otomatis saat tier utama gagal, tanpa downtime bagi pengguna.

    Enkripsi REST Payload:
    Enkripsi AES-256-CBC + HMAC-SHA256 pada Dio interceptor saat ini hanya
    diterapkan pada request Edge Function update-pin dan respons sukses
    terenkripsinya. client-error-log dan endpoint Supabase lainnya memakai
    JSON/binary biasa melalui HTTPS. Field-level encryption tersedia sebagai
    helper namun bukan lapisan yang otomatis dipasang pada semua API.
    Env vars yang dibutuhkan: REST_ENCRYPT_KEY (64 hex chars) dan REST_HMAC_KEY (>=64 hex chars).

    post:
      tags:

      summary: Update PIN via Edge Function (server-side)
      description: >-
        Supabase Edge Function untuk update PIN secara aman dari client tanpa
        mengekspos service-role key. Berjalan di server-side (Deno runtime).
        
        **Kapan digunakan:**
        - Reset PIN tanpa session — saat ini belum aman untuk production karena
          OTP tidak diverifikasi oleh function ini.
        
        **Keamanan:**
        - Wajib mengirim Authorization: Bearer dan apikey.
        - Session valid dibatasi ke profil pemilik session; token anon bukan
          bukti identitas untuk reset PIN.
        - Service-role key hanya di server-side
        - Cegah user update PIN user lain (jika punya session)
        - Rollback otomatis jika sync auth password gagal
        - Hanya request dan response sukses yang memakai envelope AES-256-CBC + HMAC-SHA256 melalui RestCryptoInterceptor.
        - Error response tetap JSON biasa melalui HTTPS.
        
        **Alur:**
        1. Validasi Authorization header Bearer (JWT sesi pengguna atau anon
           key untuk alur tanpa sesi; anon key bukan bukti OTP).
        2. Cek session — jika ada, pastikan profile_id = user.id
        3. Ambil pin_hash lama (untuk rollback)
        4. Update pin_hash di tabel profiles
        5. Sync password ke Supabase Auth via admin.updateUserById
        6. Jika gagal → rollback pin_hash lama
        7. Return success/error response
        
        Alur ganti PIN dengan session aktif tidak memanggil function ini; client
        memperbarui /rest/v1/profiles lalu menyinkronkan password melalui
        /auth/v1/user.
