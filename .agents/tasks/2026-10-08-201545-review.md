# AES-256-CBC + HMAC-SHA256 REST Encryption Layer

This change adds a symmetric encryption layer on top of Dio for selected sensitive endpoints. A `RestCrypto` utility handles encrypt/decrypt with AES-256-CBC and HMAC-SHA256; a `RestCryptoInterceptor` hooks into the Dio pipeline; and `SupabaseAuthService.apiClient` registers the interceptor. Keys are read from `.env` at runtime. The selective path list currently covers `/functions/v1/update-pin` and `/functions/v1/client-error-log`.

Watch for: **(confirmed)** the interceptor catches and discards `SecurityException`, meaning a tampered response passes through to the caller undetected. **(confirmed)** the test suite loads the same literal keys as production `.env`, making the test keys a permanent fixture rather than test-only values. **(confirmed)** no key-length validation — a wrong-length `.env` value causes a cryptic `StateError` or an `encrypt` package exception at call time with no actionable diagnostic.

**Verdict**: CHANGES_REQUESTED

## High-level view

`RestCrypto` is structurally sound: random IV per call via `enc.IV.fromSecureRandom(16)`, HMAC verified before decrypt, `SecurityException` defined and thrown on mismatch. The wire format (`data`/`iv`/`sig`) and HMAC construction (`ivB64.cipherB64`) are consistent between encrypt and decrypt paths.

The interceptor's exception handling undoes the tamper-detection guarantee. Both `onRequest` and `onResponse` catch all exceptions — including `SecurityException` — log a `debugPrint`, and call `handler.next` anyway. A tampered response reaches the caller as though nothing happened; an encryption failure sends the raw plaintext payload when the path matches an encrypted endpoint.

The test suite covers the three critical paths (round-trip, selective field encryption, tamper detection) but sets up dotenv with hardcoded hex strings that are identical to the production `.env` values. If those keys are ever rotated in production the tests silently diverge; if the test file is ever read by a developer copying "test" values, they acquire the production keys.

The interceptor is additive and has no logic that touches Supabase's own REST paths (`/rest/v1/*`, `/auth/v1/*`), so non-regression is intact.

<details>
<summary>Issues (4)</summary>

1. **HMAC tamper detection bypassed in interceptor** — `onResponse` catches `SecurityException` and calls `handler.next(response)` with the tampered/undecrypted data. The entire point of verify-before-decrypt is nullified. The catch block should call `handler.reject(DioException(...))` on `SecurityException`, not proceed. Same applies to `onRequest`: an encryption failure currently sends plaintext on an encrypted path.

2. **Test keys are identical to production keys** — `rest_crypto_test.dart` hardcodes the same hex strings that are in `.env`. Tests should use independently generated values; production keys must not appear in source-controlled test files. Rotate the production keys and supply distinct test keys via `dotenv.testLoad`.

3. **No key-length validation in `_getAesKey` / `_getHmacKey`** — AES-256 requires exactly 32 bytes; the `encrypt` package will throw an opaque error if given the wrong length. Add an explicit length assertion after `_hexToBytes` with a clear message, e.g. `if (bytes.length != 32) throw StateError('REST_ENCRYPT_KEY must be 32 bytes (64 hex chars), got ${bytes.length}')`.

4. **Non-constant-time HMAC comparison** — `sig != expectedSig` is a Dart string equality check, which is not guaranteed constant-time and is theoretically vulnerable to timing side-channels in a remote-call scenario. Use `crypto`'s `SecureComparator` or a constant-time byte-by-byte comparison. Low-severity given the mobile context, but worth fixing given the library already imports `crypto`.

### HMAC tamper detection neutralized by interceptor catch-all

`RestCrypto.decryptPayload` correctly throws `SecurityException('HMAC signature mismatch — payload may be tampered')` when `sig != expectedSig`. The problem is what happens next:

```dart
// rest_crypto_interceptor.dart — onResponse
} catch (e) {
  debugPrint('[RestCrypto] Decrypt error: $e');
}
handler.next(response);   // ← always called, even after SecurityException
```

The catch block logs the exception and falls through; `handler.next(response)` propagates the original encrypted (or tampered) map to the caller. From the caller's perspective the response is silently corrupt — a `Map` with keys `data`, `iv`, `sig` instead of the expected decrypted payload, with no error raised.

The fix is to distinguish `SecurityException` (and decrypt failures generally) from benign non-encrypted responses:

```dart
} on SecurityException catch (e) {
  handler.reject(DioException(
    requestOptions: response.requestOptions,
    error: e,
    message: 'Payload integrity check failed',
    type: DioExceptionType.badResponse,
  ));
  return;
} catch (e) {
  debugPrint('[RestCrypto] Decrypt error: $e');
}
handler.next(response);
```

The `onRequest` path has the same issue: an encryption failure logs and then sends plaintext on a path that the server expects to be encrypted. That should also reject rather than proceed.

### Test keys identical to production keys

`rest_crypto_test.dart` line 6-7:
```
REST_ENCRYPT_KEY=4b3c2d1e0f9a8b7c6d5e4f3a2b1c0d9e8f7a6b5c4d3e2f1a0b9c8d7e6f5a4b3c
REST_HMAC_KEY=a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2
```

These are byte-for-byte identical to the values in `.env`. The `.env` file is gitignored, but the test file is not. Anyone who clones the repository and reads the test now has the production keys. Generate independent test keys and rotate the production keys immediately.

### Non-constant-time HMAC comparison

```dart
if (sig != expectedSig) {
  throw SecurityException('HMAC signature mismatch — payload may be tampered');
}
```

Dart's `String ==` operator is not constant-time. In a mobile client calling a local-ish backend the timing channel is far harder to exploit than in a server-to-server context, but the `crypto` package already provides `Hmac.convert` which returns a `Digest`. Comparing `Digest` objects via their `bytes` lists with a constant-time loop removes the concern entirely at negligible cost.

### Test coverage assessment

The three test cases in `rest_crypto_test.dart` cover round-trip integrity, selective field encryption (non-sensitive fields pass through, sensitive fields become envelope maps), and tamper detection at the `RestCrypto` layer. What's not tested: the interceptor behavior on a tampered response (which would have caught the catch-all bug above), key-missing or key-wrong-length error paths, and `decryptSensitiveFields` round-trip.
